# Development Philosophy · 开发哲学

> 这里记录 Aaron 对“怎样才算把产品做好”的长期判断。它不是项目计划，也不是技术词典；每篇都是可以指导取舍、设计质量门槛与复盘的问题框架。

## 原则

| 原则 | 一句话 | 状态 |
|---|---|---|
| [Visibility Is a Product Requirement](visibility-is-a-product-requirement.md) | 看不见用户、系统与反馈，就无法真正经营产品。 | growing |
| [Distribution Is a Product Requirement](distribution-is-a-product-requirement.md) | 没有可行的分发渠道，产品就没有腿，无法跑到用户面前。 | growing |
| [Project Harness Is AI Autonomy Infrastructure](project-harness-is-ai-autonomy-infrastructure.md) | 项目 Harness 让 AI 能理解边界、行动、验证并从中断中恢复。 | growing |

## 写作约定

- 一条原则一篇 Markdown，文件名使用英文 kebab-case，正文以中文为主。
- 先写清它要求什么、为什么重要，再定义最低可接受标准和常见误区。
- 原则应能改变真实决策：项目在上线前、迭代中或复盘时，都能据此提出具体问题。
- `seedling` 表示刚捕捉的判断；`growing` 表示已有可执行标准；`evergreen` 表示经过多个项目验证与修订。
