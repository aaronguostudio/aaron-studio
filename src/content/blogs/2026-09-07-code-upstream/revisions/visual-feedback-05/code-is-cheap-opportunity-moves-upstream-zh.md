# AI 越能写代码，程序员越该走进业务

![工程师把产品原型带到客户的工作台上](imgs/web/00-cover-v1.webp)

很多年前在亚马逊工作时，我就有这样一个判断：一家公司有能力提供很多体面的岗位，并不意味着它需要同样规模的团队，才能创造那些业务价值。

在我看来，组织扩张有时也受到部门利益、管理层级和内部政治的推动。团队更大了，协调工作更多了，但客户真正需要解决的问题，未必以同样的速度增加。一个人可以非常忙，他的能力却被消耗在组织自身制造的工作里。

所以，后来看到亚马逊的组织调整和裁员消息，我并不惊讶。2024 年，公司就提出减少管理层级和多余流程；2025 年，Andy Jassy 又表示，广泛使用 AI 带来的效率提升，预计会减少未来几年的公司职能岗位总量；2026 年 1 月的新一轮裁员说明，仍然强调减少层级和官僚流程。[组织调整](https://www.aboutamazon.com/news/company-news/ceo-andy-jassy-latest-update-on-amazon-return-to-office-manager-team-ratio) · [Jassy 对 AI 的预期](https://www.aboutamazon.com/news/company-news/amazon-ceo-andy-jassy-on-generative-ai) · [裁员说明](https://www.aboutamazon.com/news/company-news/amazon-layoffs-corporate-jan-2026)

我的判断是，AI 降低一部分执行成本以后，也在加快企业重新审视原有的分工和人员配置。裁员本身无法衡量一个人的贡献，但它提醒我认真思考：自己积累的能力，究竟怎样连接到真实的需求。

**准备未来五到十年，我会把职业成长的重心放在理解客户、判断产品和承担结果上。** AI 给了工程师更强的执行能力，我们应该用它扩大自己能解决的问题，主动参与决定什么值得做。

## 实现变容易，值得重新安排自己的时间

最近几场工程师访谈，让这种变化变得很具体。Boris Cherny 在与 Lenny 的访谈中介绍，自己当时已让 Claude Code 编写代码，仍然亲自检查结果；Simon Willison 则谈到，可以快速试几种原型，再通过真实用户测试来帮助选择。两人的实践都让我看到：当实现能交给工具更多一些，工程师就有空间改变自己的工作安排。[Boris 的实践](https://www.youtube.com/watch?v=We7BZVKbCVw&t=977s) · [Simon 的原型探索](https://www.youtube.com/watch?v=wc8FBhQtdsA&t=1287s)

这让我想到软件发展里一条很长的线索。Dennis Ritchie 回顾 C 语言历史时，谈到高于汇编的语言让程序更容易编写和理解。之后的库、框架和工具，也不断帮开发者少处理一些重复细节。AI 又把一部分实现工作交给了 agent，连尝试一个方案的方式都在变化。[Ritchie 的回顾](https://www.nokia.com/bell-labs/about/dennis-m-ritchie/chist.html)

我最在意的是，这些进步给了我们重新安排时间的机会。以前一个想法可能光是实现，就占满了一个人的精力。现在，在适合交给 AI 的任务上，我们可以把腾出来的时间用在更早的判断，也可以跟到更晚的使用结果。

懂业务一直有价值。今天更值得主动投入，是因为理解到的一个需求，有了更低成本被验证、被实现的可能。工程师可以把这些能力放进同一个项目里练习。我想提出五个具体建议。

## 1. 深入一个行业

选一个你愿意长期理解的行业，持续弄清它怎样运作。

谁在使用产品，谁作购买决定，一项工作从哪里开始、到哪里结束，出了错由谁承担后果——这些问题值得和技术一起学。它们决定一个功能在业务里意味着什么，也决定你提出的方案能不能成立。

Kent Beck 在访谈中用薪资软件举例：算出一个金额，只覆盖了产品可见的一部分，背后还有完整的业务责任。对工程师来说，这种提醒很有分量。看起来相似的界面，放进不同业务里，可能承担完全不同的事情。[相关访谈](https://www.youtube.com/watch?v=ddHQQtjIOpw&t=8053s)

AI 让尝试新技术、搭出初版更方便，我会把一部分学习时间留给这些背景。沿着正在做的项目，画清一项业务的完整过程，把反复出现的例外、角色和决策记下来，再在下一次项目里检验自己的理解。

几年下来，这种积累可能让你看见别人还没写进需求文档的问题：几个客户为什么反复卡在同一处，现有产品为什么一直没有解决它，什么条件改变后终于值得动手。行业经验的价值，会在这样的判断里显现。

## 2. 走到客户身边

主动争取参与客户沟通，去看产品在什么情况下被需要，又为什么被放弃。

需求文档通常已经是整理过的答案。要理解答案背后的问题，可以请使用者演示一次真实操作：他现在怎样完成这件事，在哪一步停下来找人确认，什么错误会让他重做。看到这些过程，你才能判断一项改动究竟帮到了哪里。

比如，假设你想做一个自动整理业务单据的工具。演示里识别得很漂亮，客户却可能最在意少见的例外：谁来确认，出错后怎样追回，能否继续使用现有系统。真正让他愿意采用的，也许是最后这段流程被接好了。

这会影响你接下来怎么做。原来准备优化识别界面，现在可能应该先验证异常处理；原来以为使用者最关心速度，实际看到的却是他不敢相信结果。工程师直接参与这些沟通，就有机会在大量实现工作开始前，修正方向。

我希望把省下来的编码时间，用一部分在这里。下一次接到需求，争取跟使用者谈一次；交付以后，再看他是否真的用起来。持续接触同一类客户，才有机会逐渐分清一时的偏好、反复发生的困难，以及值得认真解决的共同需求。

![观察客户在真实工作中停下来确认的地方](imgs/web/01-watch-the-work-v1.webp)

## 3. 练习产品取舍

实现更容易以后，要更认真地决定先做什么、做到什么程度，以及什么可以不做。

Simon Willison 在访谈里说，为一个设计，他经常会尝试三种原型，再比较实际效果。他也很看重传统的可用性测试：让真实用户操作，观察他们在哪里遇到困难。这里最值得我借鉴的，是把更便宜的实现用来帮助选择。[相关访谈，22:11 起](https://www.youtube.com/watch?v=wc8FBhQtdsA&t=1331s)

还是拿前面那个假设的单据工具来说，可以试着让用户逐项核对，也可以只突出需要处理的例外。两种方案都能做出来以后，就有条件比较：哪个更容易看懂，哪一步仍需要解释，用户是否完成了原来要做的事。这样的反馈，比在脑子里反复推演一个完美方案更有帮助。

我会建议工程师为一个重要的产品选择，做一次小范围比较。开工前写下最想验证的问题，做完以后再看它有没有得到回答。AI 提出的方案也放进这个过程里，用同样的实际反馈来检验。

产品判断是在这些取舍里练出来的。你逐渐知道一个功能为什么值得保留，一段流程为什么应该缩短，哪些复杂性确实来自业务。实现能力越强，越值得用这样的判断来决定它的方向。

![在两种纸面方案之间比较和选择](imgs/web/02-choose-the-path-v1.webp)

## 4. 验证商业价值

想探索自己的产品或生意，就尽早弄清客户为什么愿意付出代价来使用它。

这包括钱，也包括迁移、学习、接入和信任的成本。客户已经有一种处理问题的办法，你需要了解那种办法为何一直被使用，以及自己的方案改善了什么，才足以让他改变。

Simon 在《Writing code is cheap now》里讨论过：许多开发取舍建立在编码昂贵这个前提上，agent 改变了其中一部分成本。我认为，这也给了工程师重看商业机会的理由。过去因为开发投入太大而搁置的需求，现在值得重新估算。[原文](https://simonwillison.net/guides/agentic-engineering-patterns/code-is-cheap/)

估算时，也要把模型用量、接入、维护和支持放进去。接着去接触潜在客户，看看他是否愿意花时间试用，是否愿意讨论实际接入，谁能决定预算。研究客户在哪里寻找方案、现在比较哪些产品，会让你更清楚怎样把产品带到他们面前。

这些都是工程师可以主动学习的事情。即使做的是内部工具，也可以弄清它减少了什么等待、返工或重复劳动，再观察使用者有没有因此改变工作方式。每次尝试都应该帮你更接近一个答案：这个东西在现实中有什么价值。

我希望更多工程师认真试一试这种探索。已有的技术能力，加上越来越强的执行工具，给了我们把想法拿到市场里检验的条件。商业判断需要从接触市场开始积累。

## 5. 把项目带到使用

主动负责一个范围明确的项目，从需求跟到交付，再跟到使用反馈。

Microsoft Digital 在今年 9 月的一篇实践文章中提到，个人开发变快以后，团队最初并没有同步提速；他们随后把业务意图和验收标准放进共同维护的规格中。这是该团队对自身实践的总结，也说明为什么值得把注意力放到整项工作的连接处。[Microsoft Digital 的实践](https://www.microsoft.com/insidetrack/blog/engineering-the-frontier-firm-sharing-our-ai-native-approach-to-software-development/)

目标有没有在交接中走样，系统之间有没有接好，出错以后有没有人能处理，使用者是否知道怎样开始——这些都影响一个项目能否真正交出去。AI 能帮忙推进更多环节，工程师就更有条件把它们连起来，保持对整个任务的理解。

我最近也用 AI 推进过一个跨系统的报表任务，在开发环境完成了验证，这段经历让我更愿意承担完整任务；具体过程已写在[之前的博客](/zh/blogs/gpt-6-astra-real-work)里。

工程经验在这里有很具体的用途。测试需要覆盖真实的失败情形，日志要帮助定位问题，设计要考虑后续维护，验收要有可核对的结果。把这些事情做好，才能让别人放心使用你交付的东西。

下一个项目，可以提前约定怎样才算完成，交付以后再回访一次。沿着整条过程看，哪些判断对了、哪里返工了、使用者最终得到了什么。这种经验会帮助你承担下一项更复杂的工作。

## 为未来积累更完整的能力

很多年前在亚马逊时的那个判断，至今仍影响着我：组织可以提供一个岗位，自己的能力却需要持续连接到真实需求。我想更清楚地知道，投入的时间怎样变成别人需要的价值。

所以，我愿意把接下来几年的精力投在这些事情上：深入一个行业，认识它的客户，理解其中的生意，用产品检验判断，再把值得做的事情推进到实际使用。每一个项目，都可以同时成为创造价值和积累能力的机会。

如果五年、十年后，AI 能承担比今天更多的工作，我希望那时的自己也已经看懂了更多需求，能作出更好的取舍，带着一个想法走到被人使用。这样的成长，需要从今天的一次客户沟通、一次产品尝试、一个完整项目开始。

想到这里，我对工程师的未来仍然充满期待。越来越强的工具，让我们有机会亲自探索原本碰不到的业务，尝试原本做不起的产品。**我想用好这次机会，把自己真正想做、也确实有人需要的事情做成。**

*资料核对：2026 年 9 月 7 日。Amazon 部分结合我的个人判断与公司公开说明；访谈为关键段落转述。单据工具是说明性的假设，五项建议及未来展望是我的综合判断。*
