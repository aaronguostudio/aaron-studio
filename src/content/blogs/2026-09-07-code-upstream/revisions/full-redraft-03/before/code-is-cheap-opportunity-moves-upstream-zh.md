# 代码越来越便宜，程序员的机会在前移

假设你收到一个需求：给这个页面加上“导出 Excel”。

对一个熟悉项目的 agent 来说，实现按钮、接口和文件生成，可能已经不需要你逐行去写。你检查一下结果，补上测试，就能继续下一个任务。

但我越来越想多问一句：**导出以后，那个人还要做什么？**

他也许要把几张表拼起来，找出漏掉的事项，再逐个联系负责人。如果我们只完成了导出，代码任务结束了，他最费劲的工作却还在那里。

最近关于 AI 编程的几场讨论，让我反复想到这件事。实现越来越容易以后，程序员有机会把更多精力放到工作的前面：理解业务，找出真正的问题，参与决定什么值得做。这就是我说的“机会在前移”。

Boris Cherny 在今年 2 月与 Lenny 的访谈里说，他当时的代码已经全部由 Claude Code 编写。但紧接着，他也说自己仍然看代码，团队保留人工 review。放在一起听，这两句话才完整：AI 能接手大量实现，工程师仍然需要对交出去的东西有把握。[原访谈，16:17–17:31](https://www.youtube.com/watch?v=We7BZVKbCVw&t=977s)

我的感觉是，有些讨论还停留在代码由谁写、哪个模型写得更好。这些问题当然值得研究。我更想知道的是，当我们有能力更快做出东西以后，愿不愿意往前走一步，去发现那些还没有被写成开发任务的需求。

## 抽象一直在帮我们少做一些事

计算机的发展里，这种变化并不陌生。Dennis Ritchie 回顾 C 语言历史时，提到他们希望保留高于汇编的语言所带来的好处：程序更容易编写，也更容易理解。[Ritchie 的历史回顾](https://www.nokia.com/bell-labs/about/dennis-m-ritchie/chist.html)

从语言到库和框架，把反复出现的实现工作封装起来，一直是软件开发的一条重要路线。开发者因而可以直接表达更接近目标的东西。

这不是一条旧语言被新语言依次淘汰的直线。底层系统仍然需要专门知识，业务的复杂性也不会因为表达工具更好就消失。AI 又有一个需要留意的区别：它生成的方案可能误解目标，不能像调用一个行为明确的库那样，默认结果可靠。

这也不要求每个程序员都转成产品经理。做底层系统、性能或安全的人，仍然需要很深的技术能力；AI 同样可以参与需求分析和方案选择。我关心的是，工程师怎样把已有经验用到更早的判断里。

工具不断接手原先需要人亲手完成的细节，我们也需要重新安排自己的注意力。对今天的程序员，我想提六个建议。

## 1. 走近真实工作

收到需求以后，先看看提出需求的人怎样完成这件事。

拿前面那个假设来说，单看工单，我们可能讨论导出格式、字段和下载速度。跟着使用者走一遍，就会看到他为什么反复下载，怎样比对不同文件，又在哪里容易遗漏。

这些信息会改变方案。也许只需要保留导出；也许增加一个待处理列表更有用；也可能问题出在几个系统对同一件事的定义不一致，做一个更漂亮的页面解决不了。

不必一上来就做完整的业务调研。下一次接需求时，可以请对方演示一次实际操作，看他在哪一步停下来、复制数据、找人确认。工程师懂得系统能做什么，走近这些现场以后，也更容易发现哪些麻烦原本可以少一点。

## 2. 把结果说清

理解了问题，还要把“怎样才算做好”说清楚。

“加一个待处理列表”仍然有很多空白。什么情况算待处理？谁能看？已处理的事项什么时候消失？数据还没更新时，页面应该怎样提醒？这些决定没有说清，agent 就只能用看似合理的默认值往下做。

Microsoft Digital 在 9 月 3 日发布的一篇实践文章中，介绍了他们把业务意图、边界情况和验收标准放进持续更新的规格文档的做法。这是微软自身的经验描述，却很具体地呈现了工程师工作重心的一种变化。[Microsoft Digital 的实践](https://www.microsoft.com/insidetrack/blog/engineering-the-frontier-firm-sharing-our-ai-native-approach-to-software-development/)

我觉得可以从很小的地方开始：开工前，写清楚谁要完成什么、哪些情况不能做错，以及用什么例子验收。写到足以检验当前想法就可以开始尝试，后面的反馈再带回来修改。AI 可以帮助追问和整理；最后仍要有人确认，这些句子确实代表了业务需要。

## 3. 用原型求证

需求说得清楚，也可能选错了方案。实现更容易，最值得利用的地方之一，是早点发现自己想错了。

Simon Willison 在 4 月与 Lenny 的访谈里谈到，他会为一个功能尝试几种原型，再比较怎样用起来更合适。他仍然看重真人试用：观察一个实际使用者操作，比让 AI 扮演用户更能让他信服。[原访谈，21:27–23:35](https://www.youtube.com/watch?v=wc8FBhQtdsA&t=1287s)

回到那个导出需求。与其先把整套待处理系统做完，可以先做一个很小的页面，让对方用样例数据找出需要跟进的事项。你要观察的是：他能否找到、是否看得懂、还需不需要回到原来的表格。

这样做的价值，是让一次实现回答一个问题。必要的权限和数据边界照样要守住，原型则尽量围绕当前最不确定的地方展开。发现方向不对，改掉它，也是一种进展。

## 4. 交付整件事

我最近做过一个业务报表任务。应用运行在 Linux 上，报表引擎却需要 Windows。要让业务系统真正拿到报表，就得把请求、数据库连接、PDF 生成和附件返回接起来。

展开后，它涉及 Azure 资源、网络配置、Windows 服务和 SQL 证书等问题。AI 在授权范围内把这些工作连着往前推进，最终在 Dev 环境跑通了报表链路，也完成了附件验证。[我的实际使用记录](/zh/blogs/gpt-6-astra-real-work)

这次经历让我感到，工程师可以接住更完整的一项任务了。单独交付一个服务，还不能说明报表已经可用；任务是否完成，要沿着业务实际会走的路看。

所以我愿意在接需求时多问一圈：它从哪里来，经过哪些系统，最后交到谁手里？有了 agent 帮忙执行，我们可以把更多注意力放在这些连接处，减少“我的部分已经做完了，但整件事还不能用”的落差。

## 5. 拿证据讲质量

业务越重要，工程质量越有具体的含义。

前面的报表如果重试一次，会不会生成重复附件？请求失败以后，使用者能不能知道出了什么问题？这些都需要检查。对工程师来说，测试、日志、代码审查和系统知识，正好可以用来回答这些问题。

Kent Beck 在 7 月的访谈里，用薪资软件提醒人们注意这层区别：算出一个金额，只覆盖了产品能看见的一小部分；完整业务还包含很多不容易从界面看出来的责任。[原访谈，2:14:13–2:15:39](https://www.youtube.com/watch?v=ddHQQtjIOpw&t=8053s)

我更愿意把技术讨论落到这里。某个设计更复杂，是否因为它必须处理真实存在的失败情形？某项测试通过了，是否足以说明使用者关心的行为正确？agent 说“已完成”，我们手里有没有可以核对的结果？

代码可以由 AI 写，判断和验证也可以得到 AI 的帮助。但把结果交出去的人，仍然需要知道自己凭什么相信它。

## 6. 重看小需求

还有一类机会，容易被热闹的新产品掩盖：那些一直存在，只是以前不值得专门开发的小问题。

一个转换格式的小工具，一个减少重复录入的步骤，一个让同事不必每次都找你处理的页面。过去你也许知道怎样做，只是排不上时间。实现成本变了，这些旧判断值得重新算一次。Simon 在自己的文章里也讨论了编码变便宜后，原有成本取舍需要被重新审视。[Writing code is cheap now](https://simonwillison.net/guides/agentic-engineering-patterns/code-is-cheap/)

可以翻一翻过去因为“不值得花时间”而搁置的需求，挑一个反复出现、范围很小的麻烦，重新估算一次。把接入、维护、权限和使用成本也算进去；值得试，就做出能用的版本，再看它是否真的让人少做了一些事。一个没人再打开的工具，写得再快也没有意义。

我对这种机会很有兴趣。它可能不需要一个新公司，也未必值得发一场发布会，却可能让几个人每天的工作轻松一点。

## 把技术带到问题发生的地方

我赞同的变化，最终是工程师可以更早地介入一件事：当别人还在解释哪里难用、哪里费时间，我们就有能力参与，把零散的麻烦变成可以检验的方案。实现成本下降，给了这种参与更多空间。

过去积累的技术经验也能在这里继续发挥作用。我们知道系统怎样连接，哪些默认值有风险，什么结果值得怀疑。有了 agent 帮忙执行，这些判断可以贯穿从发现问题到实际使用的过程。

所以，再碰到“导出 Excel”这样的需求，我希望自己能既把功能做好，也愿意看看导出之后发生了什么。那里也许藏着一个更值得解决的问题。

这让我对程序员接下来的工作仍然很有兴趣。那些真实存在、却一直被将就着处理的麻烦，开始有了更多被解决的可能。**我希望把 AI 带来的执行能力，用在这些地方。**

*资料核对：2026 年 9 月 7 日。三场访谈分别发布于 2 月、4 月和 7 月；文中为关键段落的转述。“机会前移”及六条建议是我的综合判断，开头的导出需求是说明性的假设场景。*
