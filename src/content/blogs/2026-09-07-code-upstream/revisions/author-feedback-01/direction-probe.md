# AI 越能写代码，程序员越该走进业务

这是开头、一节正文和结尾的方向试写，供评审立场与论证。尚未替换全文；章节之间并非连续成稿。

## 开头试写

我对 AI 编程的判断很明确：程序员应该把更多精力投入业务，参与决定做什么，并主动承担把一项工作做成的责任。AI 已经给了我们更强的执行能力，值得用它扩大自己能解决的问题。

最近做一个跨 Linux 和 Windows 的业务报表任务时，我感受到了这种变化。云资源、网络、服务安装和数据库连接，可以放在同一个任务里，让 AI 连续推进。我仍然要理解目标、作出取舍、确认结果，但执行已经不必处处由我亲手完成。

这让我开始重新考虑接下来几年的成长。如果 agent 继续承担更多实现工作，我希望五年、十年后的自己，能够深入理解一类业务，判断什么值得做，并带着一个项目走到实际使用。我愿意从现在开始，为这种能力投入时间。

技术进步让我兴奋的地方正在这里：以前有想法，也懂技术，仍然会被大量实现工作挡住。现在，更多想法值得认真尝试。工程师可以更早参与一件事，连问题该怎样解决，都有机会亲自推动。

## 正文试写：主动负责完整项目

我建议工程师主动争取一个范围明确的项目，从需求一直跟到使用。把它当作自己的成长机会。

那次报表任务的目标，是让业务系统拿到可以使用的报表。为此，运行在 Linux 上的应用需要把请求交给 Windows，连接数据库，生成 PDF，再把附件返回。任何一个环节没有接好，交付都没有完成。最后，我们在 Dev 环境跑通了这条链路，并验证了附件。[之前记录的实际过程](https://www.aaronguo.com/zh/blogs/gpt-6-astra-real-work)

这段经历让我看到，自己可以在一个任务里保持更完整的理解：为什么要做、系统怎样连接、什么地方失败过、凭什么判断结果可信。AI 接下了一部分执行工作，我就有更多空间把这些事情连起来。

把时间拉长，这种经验值得反复积累。参与一个项目，就看懂一段完整业务；推进下一个项目时，再把这份理解用进去。几年下来，你会更清楚哪些需求值得先做、哪些方案会在真实使用中出问题，以及什么时候已经做到了足够好。

微软自己的经历也说明了为什么要看整件事。他们发现个人开发变快以后，团队并没有同步提速，随后才把更多注意力放到业务意图与共同的验收标准上。这个案例给我的启发是：交付能力需要沿着整个任务建立，单个环节的产出无法替它回答问题。[Microsoft Digital 的实践](https://www.microsoft.com/insidetrack/blog/engineering-the-frontier-firm-sharing-our-ai-native-approach-to-software-development/)

下一次，挑一个你有条件负责的小项目，把需求、实现、验收和反馈真正接起来。大小可以渐进，理解要完整。你练到的，是把技术变成别人能使用的结果的能力。

## 结尾试写

我希望程序员认真对待这次机会。去了解一门业务，找出一个反复发生的问题，带着 AI 把它做成，再从实际使用里修正判断。这些经历会决定我们接下来能承担什么。

我愿意把未来几年的精力投在这里。工具会继续变化，新的能力也会继续出现；每次进步，都给了我尝试下一件事的理由。

想到那些因为太费时间、太难协调而被搁置的想法，我对未来仍然很有期待。有些可以成为产品，有些能改善团队的工作，有些只是解决一个自己在意的问题。我想用好手里越来越强的工具，让其中更多事情真正发生。
