# 这篇稿子为什么不成立

结论：Aaron 的批评准确。稿子保留了主题词，却没有把他的判断发展成有分量的论证。需要重写论证，再处理文字。

## 1. 写出了主题，没有写出选择

“走近真实工作”“把结果说清”“用原型求证”都合理，但读者仍不知道作者究竟要求他们如何重新安排职业投入。

更值得表达的主张是：程序员应该主动参与业务判断，并借助 AI 承担完整项目；未来几年的能力积累，应围绕能够解决的问题展开。

“有机会多问一句”“也许藏着一个问题”只能传达轻微好奇，承载不了这个主张。更坚定的表达必须有理由，不是把“也许”机械替换成“必须”。

## 2. 没有解释为什么是现在

把 AI 相关句子拿走，多数建议仍适用于十年前。懂业务、做原型、关注质量本来就是好习惯；文章应该解释工具变化怎样改变它们的优先级和可行性。

可以展开的推理：更多实现工作能委派 → 小范围试验和跨环节执行更容易启动 → 个人可以更早提出方案、更持续地跟进结果 → 值得提前积累行业理解、取舍能力和完整交付经验。

这是一条需要论证的推论，不是已经测量出的全行业结果。五到十年的展望应落在作者愿意如何准备，而不是预测精确的岗位数量。

## 3. 资料被压成了背书

素材并非没有，关键细节没有发挥作用。

## 4. 限定语切断了论证

稿子在主张还没立住时，已经插入“当然”“这不要求每个程序员”等旁支。一条建议刚出现，注意力就被带去解释别的东西。

必要范围要保留，例如个人案例只跑通 Dev，不能改成生产成功。关于研究方法的说明可以放来源注记。反对意见只有在改变建议的适用条件或选择时才需要展开。

## 5. 缩小了作者的期待

作者想讨论未来的职业能力与更大的创造空间。原稿用导出按钮开篇，又把机会主要收在几个小工具里。例子本身能解释问题，却撑不起整篇的志向。

价值观应该贯穿正文：技术让人有能力改善真实工作，工程师值得主动承担这些问题。热情来自这个愿望，以及已经发生的工作体验；多写几个“兴奋”“未来可期”没有帮助。

## 执行与 skill 各自的问题

shared editorial system 已经要求保留作者立场，明确说明文件完整与扫描通过不等于质量。本次模型审读仍给出 PASS，只处理四处局部问题；主要责任在编辑判断没有真正检查论证。

## 新方向

主张：AI 越能承担实现，程序员越应该深入业务、参与选题，并带着完整项目积累能力。

建议先收成五项，顺序按职业能力的发展安排；篇幅取决于证据，不保留数字配额。

1. **深入一个行业。** 跟随真实交易、成本、例外和责任去理解工作；让技术知识有持续发挥作用的场景。
2. **参与决定做什么。** 把模糊抱怨转成值得验证的问题，能解释为何先做它、暂缓另一件事。
3. **主动负责完整项目。** 从目标到实际使用保持连续理解；在明确授权和团队协作中扩大承担的范围。
4. **用原型换反馈。** 把更便宜的实现用于比较方案，让一次试验带来下一次更好的判断。
5. **掌握验收和取舍。** 用工程知识判断结果是否可靠、哪里需要继续投入；通过项目累积这份判断。

每一项正式成稿时都要有改变的原因、足够具体的材料和未来积累的意义。它们不是每节固定模板；某点论证不够就合并或删除。
