# 论证备忘录

## 核心论点

AI 代码的审查深度，不应由“代码是谁写的”或“diff 有多少行”决定，而应由这项修改如何成为系统事实决定：越接近 critical system 或 system of record，人类理解就越必须从结果与测试下沉到系统不变量、数据传播、恢复路径和关键源码。

可以被反驳的强版本：

> 我们不需要读完 AI 写出的每一行代码，但任何能够改写组织所相信之“事实”的变化，都不能在无人理解其关键路径的情况下通过。

## 为什么现在值得写

- AI 已经把实现、测试和文档的生成速度推到人类 review bandwidth 之外，“逐行读完一切”正失去可扩展性。
- 2026 年 7 月，Mitchell Hashimoto 用 “I read the code” 回答质量问题；Uncle Bob 随后公开表示不读 agent 实现，而以极端约束和最终测试承担责任。争论给出了两个看似相反、都很强的答案。
- Aaron 面对的不是抽象身份焦虑。他已经确认一条实际工作边界：一旦 AI 修改 critical system 或 system of record，他就会产生顾虑，并要求更深理解。
- 这条边界能把争论从“真正的程序员读不读代码”推进到更有用的问题：一项变化如何获得权威、跨越边界并把后果交给别人。

## 机制解释

### 1. 生成成本下降，理解成本没有同步下降

AI 可以并行生成实现、测试、文档和 reviewer 意见；人的系统理解仍主要是串行的。若所有输出都采用同样深度的逐行阅读，review 会成为吞吐瓶颈；若为了吞吐直接跳过理解，则会积累理解债。

### 2. 阅读与测试解决的是不同问题，而且都不充分

- 阅读源码提供形成 mental model、识别架构偏移和处理未知故障的机会，但“看过”不等于证明正确。
- 测试与约束能大规模检查已编码的条件，却不能证明规格完整；同一模型、同一上下文生成的实现与验证还可能共享一个盲点。
- Code review 不只生产 bug report，还生产个人理解、团队共同语言和责任归属。自动化最直接替代的是第一部分。

### 3. 真正的风险变量是修改如何成为“事实”

一个 disposable local script 即使错误，后果通常由使用者独自承担，也容易丢弃。System of record 则定义组织认可的权威状态；写入可能向报表、权限、客户体验、财务判断和下游流程传播。此时，即使代码能回滚，已经改变的数据、审计轨迹与信任也未必自动恢复。

这里要明确区分两个概念：

- **Critical system** 由失败后果定义：即使它不保存权威数据，故障也可能造成巨大 blast radius。
- **System of record** 由事实权威定义：其他人和系统会根据它的状态行动，因此错误可能持久存在并继续传播。

两者经常重合，但不是同义词。这个区别能防止文章把所有风险都粗糙地归为“数据库很重要”。

因此，真正应该 review 的单位不只是 diff，而是整条责任链：

`意图 → spec → 接口 / 不变量 → 实现 → 独立证据 → 权威写入 → 下游传播 → 恢复能力`

### 4. 审查注意力必须按风险配置

低风险、私有、短寿命、可逆的工作可以把理解停留在行为或证据层。跨团队、客户、生产或权威数据边界的修改，必须建立系统模型；critical system 与 system-of-record 关键写路径通常还要求源码级理解。

## 证据地图

### 一手事实

- Mitchell 的 “I read the code” 是对一个刚运行不到 24 小时的多模型工作流如何控制质量的回答；不能扩写成普遍规则。
- Mitchell 对 OSS human boundary 的完整表述更关键：是否 review 私人代码是个人选择，但把代码交给另一个人维护前应完成人工审查。
- Uncle Bob 并非盲信实现；他把判断上移到规格、Gherkin、QA、覆盖率、变异测试、质量指标与最终人工测试，并用 accountability 定义工程师身份。
- Godot Foundation 的 2026 policy 明确称 AI 降低 PR 生成成本，但没有降低合格 reviewer 的稀缺性，因而要求贡献者理解、维护和修复自己的提交。
- OpenAI 的 Harness Engineering 案例显示，不手写实现需要更强的环境、可执行规格、反馈回路和架构边界；其长期 coherence 仍是开放问题。

### 有边界的研究证据

- Sonar 的厂商调查显示，声明不信任 AI 代码与持续验证之间存在 gap；数字只能归于该调查。
- c-CRAB 预印本显示，其 benchmark 下 AI reviewer 更偏 robustness / testing，较弱于 design、documentation 和 maintainability；不能写成通用 bug 检出率。
- Human-AI Synergy 的观察研究支持人类 review 仍承担理解、测试判断与知识传递；不能写成因果结论。

### Aaron 的个人观察

- 既有文章已经记录：AI compresses work, but it does not compress responsibility；生成量提高后，review 成为稀缺环节。
- 本次确认的新边界：任何涉及 critical system 或 system of record 的修改都会触发顾虑与更深审查。
- 没有单次事故，不虚构时间、缺陷或损失。个人可信度来自清楚说明 decision rule，而不是戏剧化 receipt。

### Aaron 的推断与判断

- Mitchell 与 Uncle Bob 的共同原则不是“读”或“不读”，而是不把 verification debt 跨过 human boundary。
- System of record 是四级审查阶梯的最佳分界，因为它说明了什么时候代码不只是实现，而是在定义组织事实。

## 需要承认的反方观点

1. **没有源码理解就没有真正 ownership。** 测试只覆盖已想到的风险；异常和维护最终仍需要 mental model。
2. **逐行阅读也可能制造虚假安全。** 人会漏 bug，大 diff 的扫读尤其容易把“看过”误当成“理解”。
3. **风险分层可能成为偷懒借口。** 今天的临时脚本明天可能进入关键流程，团队也可能长期低估某个系统的 blast radius。
4. **资深工程师少读代码，是因为过去已经读得足够多。** 把专家的黑箱工作法直接用于 junior 培养，会损害学习与工程判断。
5. **System of record 并不是唯一风险边界。** 无状态的权限、路由、基础设施或安全修改也可能有巨大影响。

## 对反方的回应

- 同意源码理解仍重要；文章反对的是把逐行阅读当成所有变更的统一质量机制，而不是反对阅读本身。
- 四级阶梯必须是累积的：进入 L3 / L4 不会因为测试充分就跳过行为与证据，也不会因为看过源码就跳过运行验证。
- 风险分类应定期重评。只要一个“临时”工具开始共享、持续运行、写入权威数据或影响他人，最低审查层级就自动上升。
- 学习目标与 shipping risk 是两条不同轴线。Junior 可能在低风险任务上仍需要源码深读，因为目标是形成判断，而不只是放行代码。
- System of record 是 Aaron 个人边界的具体锚点，不是完整风险 taxonomy；权限、资金、隐私、删除、并发、安全与核心基础设施同样通常进入 L4。

## 可复用框架

### Review Depth Ladder / 理解深度阶梯

先问四个问题：

1. **Boundary**：修改会把后果交给谁？是否跨团队、客户、生产或权威数据边界？
2. **Blast radius**：最坏失败影响多大，是否会向下游传播？
3. **Reversibility**：能否及时发现？回滚代码能否恢复数据、审计轨迹与信任？
4. **Evidence independence**：实现、测试和 reviewer 是否可能共享同一模型、上下文和假设？

据此决定最低层级：

- **L1 Outcome**：私有、短寿命、隔离、易丢弃；验证结果。
- **L2 Evidence**：风险有界；检查测试、日志、CI、静态检查与独立 reviewer。
- **L3 System Model**：共享或生产变更；人能解释数据流、接口、依赖、不变量、失败模式和恢复。
- **L4 Source**：critical system、system of record 的写路径，以及权限、资金、隐私、删除、迁移、并发、安全和核心架构；阅读关键 diff、trace 关键路径，并验证业务不变量、权限、事务、幂等、reconciliation、审计、rollback / compensation 与下游数据恢复。

强制规则：critical system / system-of-record 修改最低 L3，关键写路径通常 L4。

## 对读者的启发

- 不要问团队是否“review AI code”；应问不同类别的变化最低需要哪一级理解，谁拥有放行权，哪些证据必须独立。
- 不要把 green tests 当成 ownership。能够说明系统如何失败、如何传播、如何恢复，才接近真正拥有变化。
- 把 review policy 从作者身份迁移到风险属性：同一段代码，无论由人还是 AI 写，只要开始改写权威状态，审查深度就必须上升。
- 文章最终要留下的战略判断：代码生成会继续便宜，但组织对“什么算事实”的控制不会因此变得不重要，反而会成为 AI-native execution 的核心资产。
