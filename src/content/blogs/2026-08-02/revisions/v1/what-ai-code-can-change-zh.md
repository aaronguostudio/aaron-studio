只要 AI coding agent 动到关键系统，或者触及 system of record（权威记录系统），我就会换一种审查方式。

我讲不出一个戏剧性的事故故事。这恰恰是重点：边界必须设在事故发生之前。

对于私有、短期、可逆的工作，我通常愿意从结果和证据判断它是否可用。但当一段代码能够改变权威状态——也就是客户、业务流程或其他系统会当成事实的东西——测试全绿就不再足够。我需要理解它的写入路径、可能破坏的不变量、错误会如何传播，以及出事后我们能不能恢复事实，而不只是回滚代码。

所以我现在问的，不只是“这段代码我读过吗？”

我会先问：**它有权改变什么？**

关键系统和 system of record 也不是同一个概念。关键系统之所以需要谨慎，是因为失败后果严重；system of record 之所以需要谨慎，是因为它的数据具有权威性。两者经常重叠，却分别从后果与权威两个方向，要求我们把审查做深。

最近我看了[一支讨论 AI 代码到底要不要读的中文视频](https://www.youtube.com/watch?v=Hh3AmV46epI)。视频里的两种答案几乎相反。

Mitchell Hashimoto 的质量控制很直接：[“I read the code.”](https://x.com/mitchellh/status/2072738025344565262) Uncle Bob 的做法则接近另一端：他不阅读 agent 生成的实现，而是在外面建立规格、测试、变异测试、质量指标、QA 和最终验证。

两种做法看似互不相容，但我认为，背后其实是同一条规则。

两个人都没有把责任交给模型。Mitchell 让人的理解贴近实现；Uncle Bob 把大量判断移到约束和证据上。他们真正的分歧，是人类理解应该落在哪一层，而不是人是否还需要为结果负责。

## 真正的分歧，是人的判断应该放在哪里

Mitchell 的简短回答，有一个容易被忽略的语境。当时他刚[介绍一套多模型协作流程](https://x.com/mitchellh/status/2072715852944957531)：一个模型做计划，一个写代码，再由另一个判断结果。那套流程使用还不到一天。“I read the code” 不是一份适用于所有场景的工程宣言，而是他对“你如何控制这次实验的质量”的回答。

他在另一条关于开源贡献的帖子里，把立场说得更完整。代码留在自己手里，审不审是个人选择；一旦把 AI 生成的代码提交给开源项目，就跨过了人与人之间的边界。另一个人将承担理解、审查、维护和修复的成本。因此，[至少做基本的人工审查，是对别人时间的尊重](https://x.com/mitchellh/status/2067970516951150721)。

Uncle Bob 把边界放在另一处。他在[原始讨论](https://x.com/unclebobmartin/status/2080257779395154409)里说，如果逐行阅读 agent 的全部实现，他就无法获得 agent 的生产力。他的替代方案是一套异常严格的验证关卡：单元测试、Gherkin 验收测试、QA 流程、覆盖率、变异测试和质量指标。人的主要精力放在前期规格定义和最终测试上。有人质疑这样是否还算工程师，他的回答很直接：“I am the engineer because I am accountable.”

两人共享的是 accountability，却未必共享对“理解到什么程度才算足够”的判断。Mitchell 把源码理解当作质量门槛；Uncle Bob 认为，一套足够强的约束系统可以替代大量源码阅读。这项分歧是真实存在的，几条帖子也不足以证明哪种方法在长期维护中更可靠。

Mitchell 通过理解实现来建立信心；Uncle Bob 让实现穿过一套可执行的约束系统。我的理解是，两种做法都在阻止模型成为后果的所有者，也都不愿把尚未完成的验证工作甩给下一个人。

这一点很重要。在大量使用 agent 的工作流里，生成可以迅速变便宜，合格的 review 却没有同步变得充足。Godot Foundation 在 [2026 年贡献政策](https://godotengine.org/article/contribution-policy-2026/)里写出了同一个问题：AI 降低了制造 pull request 的成本，却没有降低审查它们的成本。Godot 因此要求贡献者能够理解、解释、维护并修复自己提交的代码。

成本没有消失，只是越过边界，落到了别人身上。

## 代码真正危险，是它开始定义事实

Diff 的大小，并不是风险的好指标。

一个内部原型可能包含上千行 AI 生成的 UI，审查优先级却未必比五行权限判断、数据迁移、余额更新或客户状态修改更高。前者很大，但相对隔离；后者很小，却可能改变系统认定的事实。

可以想象同一段数据清洗逻辑进入三种不同场景。

最开始，它只是一个本地脚本，用来清理复制出来的 CSV。如果结果不对，我可以检查输出、丢掉文件、重新运行。停在“结果层”可能已经足够。

后来，它变成一个团队共用的内部工具。其他人开始依赖它的输出。此时我需要更强的证据：有代表性的测试、日志、转换规则的解释，以及发现异常记录的方法。即使它还没进入生产，也已经跨过了人的边界。

最后，同一段逻辑开始直接写入 system of record。这个系统可能为报表、权限、客户沟通、财务判断或其他自动流程提供数据。错误值不再停留在一份文件里。因为其他系统信任这个来源，错误会沿着依赖关系继续传播。

到了这一步，回滚部署不等于恢复现实。旧代码可以重新上线，但错误记录可能仍在；下游系统可能已经复制了数据；审计轨迹里可能已经留下基于错误状态发生的操作；客户或员工也可能据此做出了决定。恢复需要的可能是数据核对、补偿操作和明确修复，而不只是切回上一个 commit。

这正是“读或不读”这个二元问题遗漏的机制。代码获得改变权威状态的能力，或者能够制造难以逆转的后果时，风险才真正上升。

需要审查的单位，不再只是 diff，而是一项修改如何成为事实的整条路径。

## 读源码与跑测试，会以不同方式失效

阅读源码仍然重要，因为维护系统需要心智模型。遇到非典型故障时，工程师需要知道系统为什么这样设计、哪些假设支撑着它，以及异常状态可能流向哪里。只知道测试曾经通过，并不足以接手系统。

但阅读也不是正确性证明。审查者可以看完每一行，仍然漏掉 bug。巨大的 AI diff 还会放大这个问题：“我看过了”很容易变成一种审查表演——完成了检查仪式，却没有真正建立理解。

测试的失效方式不同。它可以反复执行远超人类工作记忆的路径。变异测试可以暴露松散的断言；验收测试可以用更接近业务的语言表达行为；静态检查可以执行已知的结构规则。Uncle Bob 的验证关卡有价值，正是因为它把怀疑变成了可以重复执行的东西。

但一套测试，只能为已经写进去的场景和预期提供可重复证据。它本身无法告诉我们：这些预期是否完整，是否真的描述了现实。

阅读可能暴露一个我们忘记提出的问题；测试可以在问题提出以后，不断检查答案。

还有一种 AI 特有的风险：实现、测试和审查意见若来自同一份 context，就可能共享同一个错误假设。证据看似变多，独立性却没有提高。确定性的检查器可以稳定地检查错误的问题；第二个 agent 也可能很自信地继承第一个 agent 的问题框架。

因此，我关注的不只是证据数量，还有证据独立性。真正有价值的检查，应该带来另一种犯错方式：人写下的业务不变量、生产流量回放、安全策略、数据核对查询，或者来自实现逻辑之外的真实运行行为。只换一个 prompt，并不能构成独立证据；它仍可能继承同一个模型的知识、仓库上下文和遗漏的假设。

“少读代码”最有力的反对意见，是团队会慢慢失去对系统的共同理解。我认同这个担忧。在我看来，代码审查不只负责发现缺陷，它还帮助个人建立心智模型、同步团队的语言和架构，并让责任归属变得可见。测试和 AI 审查工具最直接帮助的是第一项，对后面几项只能部分覆盖。

所以，按风险分配 review 不是接受黑箱代码的许可证。它是把有限的人类深度注意力，保留给那些最不能容忍黑箱的地方。

## 审查深度应该跟随代码的权威

我会用四个问题决定 review 需要下沉到哪一层。代码的权威和失败后果决定最低深度；作者身份与来源可以提高证据要求，却不应该降低这条底线。

1. **权威（Authority）：** 这段代码可以改变什么？哪些人或系统会把它的输出当成事实？
2. **暴露范围（Exposure）：** 谁会继承后果？错误结果或错误状态能够传播多远？
3. **恢复（Recovery）：** 我们能多快发现故障？能恢复状态，还是只能回滚代码？
4. **独立性（Independence）：** 证据是否带来了真正不同的 context、方法、模型、数据集或具名负责人，还是所有检查都继承了同一组假设？

由此，我把 review 分成四个累积层级。进入更深一层，不代表可以跳过前面的检查。

分流规则可以很直接。只有当工作仍然私有、隔离、可丢弃，而且不会产生权威状态时，才停在第 1 层。另一个人或流程开始依赖输出，但影响仍然有限、可恢复，就进入第 2 层。修改能够改变重要的共享行为、生产状态或 system of record 时，至少进入第 3 层。第 4 层留给能够制造权威事实或不可接受后果的关键路径。

### 第 1 层：结果

私有、短期、隔离、可以轻易丢弃的工作，可以只验证可见结果。一次性分析脚本或原型，在后果完全由我承担、随时可以放弃时，可以停在这一层。

但这不是把不透明代码提交给别人的许可证。边界一旦改变，层级也必须改变。

### 第 2 层：证据

对于风险有限、但已经有人使用的修改，我需要看到一套可信证据：测试、日志、CI 结果、截图、静态检查，以及采用不同 context 或方法的 review。我不仅关心测了什么，也关心什么没有测，以及这些证据能否挑战实现里的假设，而不是简单重复它们。

### 第 3 层：系统模型

当修改进入会影响他人的共享流程或生产行为，必须有一个承担责任的人能够解释接口、数据流、依赖、不变量、失败模式、可观测性和恢复方案。到了这一层，“测试都是绿的”不再是充分解释。

System-of-record 修改最低从这里开始。如果没有人说得清楚一次状态变化如何获得权威、随后流向哪里，团队就还没有理解到可以发布的程度。

### 第 4 层：关键源码路径

对于关键系统、system-of-record 写入路径、权限、资金、隐私、删除、迁移、并发、安全和核心架构，我需要理解能够制造后果的关键源码路径。

这不意味着每个 AI 生成的辅助函数都要用同样强度逐行阅读。真正要追踪的，是关键 diff，以及围绕它的业务不变量、授权、事务边界、幂等性、数据核对、审计历史、回滚与补偿操作的区别，还有下游修复路径。

对我来说，关键系统或 system of record 的修改，最低是第 3 层；涉及关键写入路径时，通常会下沉到第 4 层。

对于权威写入，我的发布规则很简单：没有具名的领域负责人，没有审过关键写路径，没有明确业务不变量，也没有可信的数据核对与恢复方案，就不能发布。

分类也会过期。一个“临时”脚本一旦开始定时运行、被多人使用、获得更高权限、持久保存数据或成为权威来源，就已经换了类别。它不能继续沿用原型时期的轻量审查标准。

## Ownership 是拥有状态转换

我以前写过，[AI 可以压缩工作，却不会压缩责任](/blogs/one-person-project-ai-coding)。Agent 能并行生成实现、测试、文档和审查摘要；人的系统理解依然稀缺，而且大多是串行的。要求人用同样深度阅读一切，会浪费 AI 带来的杠杆；假装所有生成物都已经被理解，则会制造更危险的错觉。

工程师的角色，不由是否亲手输入每一行、是否观察每个实现步骤来定义。但仅仅把名字挂在 AI 生成的 pull request 上，也不能构成 ownership。

Ownership 意味着能够解释预期的状态转换、必须保持的不变量、什么证据可以推翻现有信心、失败会如何发生，以及系统如何恢复。

这也延续了我构建[个人 AI 操作系统](/blogs/ai-became-my-operating-system)时形成的判断：执行可以离开我，高判断力的工作仍然必须回来。当 agent 可以运行更久、做得更多时，控制单位会变成一次 run 外面的[运行契约](/blogs/fable-5-managing-ai-autonomy)：权限、证据、检查点、停止条件与回滚。

这里还有一条学习边界。资深工程师可能把熟悉、边界清晰的实现当作半个黑箱，是因为多年阅读代码已经建立了识别风险的判断力。这并不意味着“跳过源码”适合正在建立这种判断力的人。

对团队来说，真正可执行的政策不应该只有一句“AI 代码必须 review”。它应该按变更类别制定：哪些修改强制进入系统模型审查？哪些需要领域 owner 阅读关键路径？什么证据必须来自实现 context 之外？谁能批准一次权威写入？在相信 rollback 之前，哪些恢复过程必须演练？

这些问题会让少数地方的 review 变重，从而让更多低风险工作真正变轻。

## 我现在会问的问题

AI 会继续降低实现成本。人的注意力不会同样变得充足。

未来不可能是“读完每一行生成代码”。Agent 产生代码、测试、文档和审查意见的速度，已经可以超过团队吸收它们的速度。但“从此没人读代码”也不是严肃的工程方法。前者容易沦为审查仪式，后者会让责任藏进自动化里。

真正要决定的，是人应该在哪里建立理解。

Mitchell 阅读实现。Uncle Bob 阅读约束和证据。他们仍然不同意后一种方法是否能产生足够的理解，但两个人都没有把模型当成承担责任的一方。

这也是我想保留的标准。我不必理解 AI 写出的每一行；但只要它能够改写业务认定的事实，或者造成业务无法接受的后果，就必须有一个承担责任的人能够解释：什么发生了改变、哪些不变量必须成立、什么证据能够推翻我们的信心，以及系统将如何恢复。

如果你也在思考同样的问题，我会在 [Ship with AI](https://shipwithai.beehiiv.com) 继续记录如何构建真正可负责的 AI-native systems。

接受一项 AI 生成的修改之前，我现在会问：如果所有测试都是绿的，但现实仍然错了，谁能解释原因，并把事实恢复回来？
