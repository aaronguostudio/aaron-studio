# Blog Production 与 SkillDev 审查

2026-09-07 · 本地审查与候选设计 · 未修改正式 skills 或 SkillDev 源码

## 判断

工作流已经能稳定生产一套完整内容；下一阶段最值得提高的是选材与编辑判断。当前系统很擅长发现缺少文件、链接和措辞问题，但还不能可靠区分“写得完整”与“真正表达了作者，而且值得读”。继续增加模板和评分项目，可能让稿件更齐整，却进一步压平作者的声音。

这不是判定两篇文章不好。两篇最终版本获得了作者认可，媒体迭代也产生了明确改善。需要吸收的是：**哪些问题仍反复依赖作者指出，而现有检查已经宣布通过。**

依据是本次对 skills、历史版本、作者反馈、扫描器与 SkillDev 实现的检查。五个历史英文稿的回放属于小样本诊断，不能证明这些规则造成了所有写作问题，也不能证明候选流程已提高质量。本次没有生成新文章或调用付费模型做对照实验。

## 优先改进六件事

### 1. 先保存作者的意思，再优化表达

DHH 初稿已有 AI 观点，仍把 Linux 兴趣放在叙事起点。Astra 初稿用“少修改几次”解释写作进步，而作者更在意读起来顺畅自然。两者都不是词汇扫描能解决的问题。

在现有 brief 加入少量作者原话、想强调的改变、真实情绪和次要话题。研究、提纲和审校都回看这份短记录。缺少关键生活细节时只补问能改变文章的一两个问题，不重新询问一套品牌定位。

### 2. 给文章不同的形状

[blog-production:148](/Users/aaronguo/Work/ag/aaron-studio/tiles/blog-production/SKILL.md:148) 默认商业观察与商业价值，[blog-write:149](/Users/aaronguo/Work/ag/aaron-studio/tiles/blog-write/SKILL.md:149) 要求可复用操作框架；`editorial-system.md` 又在 Argument Lock 要求一个可执行框架。个人回应、工作案例、发布解读因此容易被拉成同一种 operator essay。

按本篇主要意图选择结构：个人回应看共鸣与态度变化，案例看约束、过程和结果，解读看筛选、证据和解释。保留清晰、诚实、具体的共同标准；不统一强制商业价值、反常识论点、固定章节数、个人实验或行动框架。

### 3. 从素材质量提高，而不是只改句子

“Azure、Linux、Windows Worker、SQL certificate”是材料，不自动构成读者能理解的故事。先说任务和原来的困难，再让技术细节出场。可用的素材单位是有背景的场景、能支持主张的证据、真实的判断变化。

为每个部分问：这里提供了什么之前没有的东西？如果只是再次说“判断更重要”，就合并或删掉。允许源于公开案例的解释，不为满足个人锚点编造经历。来源记录是已经做对的机制，应继续保留。

### 4. 建立正面范例，替代规则堆积

现在反 AI 措辞要求很多，缺少一小组能说明“为什么这段更像 Aaron”的认可样本。建议保存 6–10 个前后对照片段，包含原意、修改理由和适用范围；每次按相关性选一两个。

同一原则只由一个文件维护。现有新结尾建议欢迎简短回收和情感落点，但 [blog-write:183](/Users/aaronguo/Work/ag/aaron-studio/tiles/blog-write/SKILL.md:183) 仍写着 “a conclusion that advances the thesis instead of summarizing”。这会让合适的总结也被误删。应改为检查是否完成表达，而不是禁用某种形式。

### 5. 审核真实问题，停止追求漂亮分数

[blog-write:210](/Users/aaronguo/Work/ag/aaron-studio/tiles/blog-write/SKILL.md:210) 要求至少五个问题和一次实质修订；评分又要求 85 分及每维度至少 70%。这些规则容易鼓励为了交差而找问题、为了通过而自我加分。

把核验与编辑判断分开：前者记录事实、引用、隐私、链接等明确状态；后者指出具体段落、读者损失和修改理由。允许无问题、平局、不确定。没有命中措辞规则只表示“未发现这些问题”，不显示为“文章质量 100”。

先用历史版本校准判断，再用新题目做固定输入下的候选对照。作者选择和读者体验是重要信号，模型评价只是辅助。减少修改次数也不能单独证明文章更好。

### 6. 简化路由和上下文，让媒体工作继续可靠

当前静态 manifest 声明了 40 项产物；两个实际目录分别有 46 和 41 个顶层 Markdown 文件。文件多不直接说明负担大，但 [blog-production:132](/Users/aaronguo/Work/ag/aaron-studio/tiles/blog-production/SKILL.md:132) 的“读目录内所有文件”会让历史记录、旧评分和当前正文争夺上下文。[路由表:175](/Users/aaronguo/Work/ag/aaron-studio/tiles/blog-production/SKILL.md:175) 又把社交素材缺失放在正文深度失败之前。

用明确的文章目录、当前 package state、内容 hash 和依赖关系决定下一步。先处理上游失败，再生成下游；只读当前阶段需要的记录。逻辑上收拢到 brief、证据、正文、审查状态四组，暂时兼容已有文件契约，不突然删除产物。

保留有效经验：双语作为 sibling editions、真实证据与示意插图分开、配图承担内容作用、声音音量稳定而音乐平滑进出、导演式停顿、改封面不重做无关音频、正确账号与 main 来源的发布核验。配图应早期发现证据缺口，正式制作仍按已接受版本执行。

## 最值得做的产品方向

SkillDev 可以先成为一个有证据的编辑调试台，而不是立即扩展为另一个通用 agent runtime。最有价值的操作是：

1. 选择一条作者反馈，看到修改前后原文、来源及版本。
2. 看到哪些规则被实际加载，哪些只是在 SKILL.md 中声明；如果没有记录，就明确显示未知。
3. 对照“机械检查通过”与“作者为什么仍然要改”，将评价按来源分开。
4. 对候选规则进行同输入对比，人工标注偏好、原因和不确定；不要自动把提高几分当作可推广。
5. 观察下游哪些资产因某次修改失效，避免重新做已经认可的音频等无关工作。

第一版只需接入这两篇文章的历史版本、明确的作者反馈和实际文件 hash。它是事后版本对比，不能伪造当时没有采集的工具时序、耗时、成本或规则因果链。真正的实时调试在后续增加可观察事件接入；无需记录或展示模型隐藏思考。

## 实施顺序与完成标准

**先校准**：修复按章节评分、明确 demo/probe 来源。验收是反例不再误过，UI 不把静态声明显示成实际执行。

**再试编辑候选**：使用 [candidate-workflow.md](./candidate-workflow.md) 与 [editorial-cases.json](./editorial-cases.json)，不变更发布及权限边界。历史样本检查意图／结尾等回归，新题目检验写作收益。只有可解释的质量收益才能支持提升为正式默认。

**最后精简并接入**：将通过的规则合并到唯一 owner，删除冲突要求，运行技能同步与必要校验。SkillDev 再接实际版本和事件证据。成功标准是更容易写出符合作者意图、具有足够背景和完整落点的文章，而不是更多节点、更多文件或更高的自评分。
