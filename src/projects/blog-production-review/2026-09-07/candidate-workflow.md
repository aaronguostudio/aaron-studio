# Blog Production：编辑流程候选稿

状态：2026-09-07 审查提案。尚未替换 `tiles/` 中的正式 skills；没有重写已发表文章。

目标：提高选材、作者表达和阅读体验，同时保留已经可靠的媒体与发布流程。先检验这份候选稿，不把新的偏好直接叠加成更多硬规则。

## 1. 先确认这篇文章为什么存在

在现有 `editorial-brief.md` 中记录以下内容，不新建另一份重复 brief：

- 作者原话：从当前请求和已认可的反馈中选取最有辨识度的两三句。保留热情、犹豫、期待等真实态度。
- 读者与承诺：谁会打开，读完最值得带走什么。
- 本篇重心：什么必须占据中心，什么只是有趣的旁枝。
- 素材边界：亲历、公开来源、作者判断、待验证假设分别是什么。
- 文章类型与语言：根据这次意图选择；用户反馈主要用中文时，可以先打磨中文，再做英文 sibling edition，不固定从英文起稿。

信息已经足够就继续。只有缺失会改变主张或叙事时，补问一到三个具体问题，例如“这次哪个瞬间改变了你的预期”。不要重复询问已知偏好，也不要要求作者为了满足模板临时做一个实验。

## 2. 按类型选择文章需要的东西

| 类型 | 优先解决 | 不强制要求 |
|---|---|---|
| 采访／阅读后的个人回应 | 哪些观点触动我；它们怎样与工作中的具体感受相遇；我现在怎么看 | 商业收益、反常识论点、可执行框架、已实施的个人实验 |
| 真实工作案例 | 原先要完成什么；约束在哪里；怎样推进；结果如何；哪些认识改变了 | 数字化收益、戏剧性失败、概括所有团队的结论 |
| 新发布／资料解读 | 新东西是什么；哪些变化值得关注；用来源和例子帮助理解；实际局限 | 所有功能都亲测、固定七八点、固定新闻摘要比例 |

可以混合，但要知道主要承诺。没有真实经历时用有出处的案例或明确标注的假设例子，不补写成作者经历。标题可以有吸引力，承诺必须由正文兑现。

## 3. 先选素材，再安排标题

从已有材料里选出最有解释力的场景、证据或观察。技术名词先交代它解决的任务；读者不应先遇见 Windows Worker，再猜它为什么存在。

用一两句说明每个候选部分对读者有什么作用。两个部分如果只是在重复同一判断，就合并。结构、节数和段落长度由内容决定。

旧文只有在能减少解释成本、补充证据或展示观点变化时才进入文章。可以检索，但没有有用的关联就不写，也不用留下象征性的回链。

为需要事实支撑的主张维护现有 `claim-ledger.md`。研究到足以支持本篇承诺即可；搜索数量和材料数量不是完成标准。来源不足时缩小主张或记录缺口。

配图需求可以此时标注：这里需要一张真实演示截图、这里需要说明复杂关系的图，还是这里只需文字。正式生成仍遵守文章和媒体锁定状态。

## 4. 草稿审查分清两件事

**可机械验证的事实与包检查**：来源、时间、数字、引用、隐私、链接、文件、双语主张一致性。逐项记录通过、失败或未知；失败应对应具体问题。

**需要编辑判断的阅读检查**：

1. 前两段是否让读者知道主题和作者为什么在意？
2. 例子是否提供足够背景，且确实支持观点？
3. 各部分是否带来新的内容，读者是否有继续读的理由？
4. 作者的热情、保留和判断是否准确，有没有被模板改写成另一种态度？
5. 标题、开头和结尾是否构成完整回应？

指出具体段落和读者会受到的影响，再决定是否修改。允许“没有实质问题”。取消“至少五个问题”和“必须再改一轮”的配额，不用总分替代判断。

语言扫描器只报告其能检测的措辞信号；无告警不表示文章质量 100 分。保留它作为辅助，避免继续扩张成模拟审美的正则评分系统。

## 5. 结尾要完成这次表达

把标题、前两段与末尾连起来读。判断正文的推进最后落在了哪里，读者是否听到了作者最终的态度。

可以简短回收要点，再写改变了什么、还有什么问题、为什么值得期待。个人回应允许以感受落下，案例可以以改变后的做法收束，解读可以以有依据的判断结束。不是每篇都需要行动指令、固定三段或同一种回扣技巧。

如果修好结尾需要一个正文没有的事实，回到证据和结构，不在末段突然加一个漂亮但无依据的结论。

## 6. 只让相关步骤失效

恢复任务时使用明确的文章目录与 `package-state.json`。只读取当前阶段所需的 canonical 文件及引用；历史稿在比较时显式加载。

顺序由真实状态决定：作者意图与证据 → 结构／草稿 → 编辑通过 → 媒体与分发 → 发布验证。先处理上游失败，不能因为缺少社交帖子就越过尚未通过的正文。

已获授权且范围清楚的工作继续完成。人类审阅节点依据现有授权与实际需求执行，不新增每一步确认。保留音频试听、发布账号、生产 main 来源等当前有效约束及用户授权。

批准应指向内容版本或 hash；改封面只刷新受影响的封面资产及相应下游产物，不重新生成无关音频。兼容现有文件契约，先以逻辑分组简化阅读，再逐步合并重复文件。

## 7. 用实际选择检验改进

从 DHH 和 Astra 提取少量“原稿 → 作者反馈 → 认可版本”的样本。记录为何更好，区分个人偏好与可复用原则。按相关性加载一两个，不把所有旧文都放进上下文。

这些历史样本用于诊断和校准。真正检验候选流程时，再用未参与规则设计的新题目，固定模型、来源和输入，比对当前与候选流程生成的版本。盲化顺序，允许平局和不确定；先看作者与读者的选择及原因，再看修改成本。

模型评审可以提供反例和理由，但与作者认可、事实审计分开显示。CTR、阅读完成度和订阅转化属于发布后的独立观察，不能倒过来证明正文一定写得好。

## 迁移边界

- `blog-production` 负责选择阶段、读取状态和控制下游失效。
- `blog-brainstorm` / `blog-outline` 负责材料、角度与结构；共享上面的 brief，不各造一个要求更重的契约。
- `blog-write` / `blog-prose-editor` 分别负责实质编辑与表达；不反复对同一标准打分。
- `blog-writing-language.md` 集中保存文风原则和正面示例；其他 skills 引用它，不复制矛盾版本。
- `editorial-system.md` 保存同一套通过条件；去掉与候选流程冲突的固定结构和评分配额。
- 媒体、来源核验、双语一致性、发布验证等有效机制继续保留。候选实验通过后才做正式整合与技能同步。
